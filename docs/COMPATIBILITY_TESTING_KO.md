# 통합 호환성 검증 실행 안내

[English](COMPATIBILITY_TESTING.md) · [검증 안내](../README_KO.md#개발과-검증) · [시나리오 사양](NATIVE_SCENARIOS_KO.md) · [제품 경계](COMPATIBILITY_KO.md)

실제 개발 워크플로를 **18개 시나리오 × 6개 모델 = 108건**으로 검사합니다. 현재 계약은 `codex-ghcp-workflows-18-v6`(schemaVersion 6)입니다. 안정성 66건·TUI 72건과는 별도 검사이며, 다른 행렬의 통과로 이 검사를 대신할 수 없습니다.

## 준비와 실행

`npm ci` 후 저장소 루트에서 필요한 검사를 선택하세요. 실모델 행렬은 설치 절차가 아닙니다.

**실행 모드 선택:** [계획·로컬 검사](#계획과-로컬-검사) · [오프라인 runtime](#오프라인-runtime) · [실모델 행렬](#실모델-행렬) · [저장된 증거 검증](#저장된-보고서-검증).

### 계획과 로컬 검사

**모델 호출·Codex 설치·Copilot 로그인이 필요하지 않습니다.** 기본 모드는 108건의 검사 사양만 출력하며 사례를 실행하지 않습니다.

```bash
npm run test:compatibility -- --plan
```

시나리오 설계는 `npm run test:scenarios`로 검사합니다. 문서만 수정했다면 `npm run test:docs`로 충분합니다. 현재 안내·명령 예제·생성 시나리오를 검사하며 예제를 실제로 실행하지는 않습니다.

### 오프라인 runtime

**모델 호출은 없습니다.** Node 22.12 이상, Codex **0.154.0**, 동작하는 OS 샌드박스를 준비하세요. [CLI 설치 단계](../README_KO.md#2-의존성-설치)를 따르면 되며 Copilot 로그인이나 브라우저는 필요하지 않습니다.

```bash
npm run test:compatibility:runtime
```

실제 Codex와 기계적인 SDK 대역·격리된 인증 환경을 사용하며, C11에서는 실제 실행기도 시작합니다. 실행기 검사이지 실모델 호환성 통과는 아닙니다. bridge 자체의 엔진 요구사항은 바꾸지 않습니다.

### 실모델 행렬

**Copilot 사용량이 발생합니다.** [runtime 준비 사항](#오프라인-runtime)과 [Copilot 계정 확인](../README_KO.md#3-설치와-계정-접근-확인)을 마치세요. OpenAI API 키는 필요하지 않습니다.

실행 전에 정확한 소스와 의존성 잠금 파일 사본을 별도로 보관하세요. 이 실행기는 소스 사본을 **자동 저장하지 않습니다.** 보고서 검증을 마칠 때까지 소스를 바꾸지 말고, 실행마다 새 출력 디렉터리를 선택하세요.

```bash
npm run test:compatibility -- --execute --output .runtime/compatibility-new-run
```

기존 출력 폴더는 덮어쓰지 않습니다. 부분 모델 선택·자동 케이스 재실행·OpenAI 기준선은 없습니다. 모델 사용 불가는 18개 blocked 슬롯으로, 공통 사전 조건 실패도 108개 행렬로 남습니다. 개별 실패 후 다음 케이스를 계속하며, 사용자 중단 시 신규 실행을 멈추고 미완료 증거를 보존합니다.

최대 4개 모델을 병렬 실행하고 케이스마다 정리 예비 8초를 포함합니다. 모든 제한을 소진하면 모델당 2,220초이며 사전 점검을 포함한 배정 추정치는 **75.5분**입니다(OS·I/O 지연 별도). 1시간은 목표이지 전체 강제 종료 제한이 아닙니다.

### 저장된 보고서 검증

**모델 호출이나 사례 재실행은 없습니다.** 실행이 끝나면 실패가 있어도 저장된 보고서를 검증하세요. 실패 종료 코드 때문에 검증이 생략되지 않도록 실행 명령과 `&&`로 연결하지 말고 별도로 수행합니다. 실행할 때와 같은 출력 디렉터리를 사용하세요.

```bash
npm run test:compatibility -- --verify .runtime/compatibility-new-run/report.json
```

## 결과 읽기

`.runtime/compatibility-new-run/report.md`는 판정·모델별 통과 수 다음에 **Cases needing attention**으로 실패 조건·기록된 오류·사례별 증거 링크를 보여줍니다. **Complete matrix**에는 108건 모두 남기고 커버리지 설명은 결과 뒤에 둡니다. 증거 검증에는 Markdown 화면이 아닌 `report.json`을 사용합니다.

**`evidenceIntegrity: true`는 108/108 통과라는 뜻이 아닙니다.** 저장한 증거와 다시 계산한 결과가 유효하다는 뜻이므로 `fullMatrixPassed`를 별도로 확인하세요. [보고서 필드와 예시](validation/README_KO.md#결과-읽기)를 참고하세요.

| 종료 코드 | 의미 |
| --- | --- |
| 0 | 유효한 계획, runtime 자체 검사 통과, 또는 실모델 **108/108** 통과 |
| 1 | 실패·차단·미지원·미완료 실행 |
| 2 | 인자·증거 오류 |

보고서의 `executionKind`로 오프라인과 실모델을 구분하세요. 나중에도 검증하려면 원래 실행 디렉터리 전체와 [실행 전에 보관한 소스·의존성 잠금 파일](#실모델-행렬)이 필요합니다.

보관한 소스 트리에 같은 의존성을 설치한 뒤, 예시 경로를 **원래 보고서의 절대 경로**로 바꿔 실행하세요.

```bash
node scripts/compatibility.mjs --verify /absolute/path/to/compatibility-run/report.json
```

안정성·TUI 실행기는 이와 달리 소스 사본을 자동 저장합니다. [검증 목록](validation/README_KO.md)의 공개 요약은 `.runtime` 원본 전체가 아니므로 `--verify`에 넣지 마세요. 일치하는 소스와 원본 증거가 없으면 독립적인 재계산은 불가능합니다. 과거 v5/v4 보고서는 v6가 아닌 당시 실행기가 필요합니다.

## 서로 다른 세 지표

| 지표 | 계산 / 값 | 의미 |
| --- | --- | --- |
| 실모델 행렬 통과율 | 통과 / **108**, 모델별 통과 / **18** | 관측한 결과입니다. 누락·미지원·차단·시간 초과도 분모에 남으며 모델별 18개 전부 통과해야 호환성 판정을 받습니다. |
| 체크리스트 설계 범위 | 기능군 20개 중 직접 12 + 절반 점수 6 + 미검증 2 = **75%** | 검토자가 정한 설계 범위이며 검사 통과율이나 기능 전체 지원율이 아닙니다. |
| 실측 제품 커버리지 | **미측정/null**, 90%는 목표 | 위 두 수치로 측정되지 않습니다. 체크리스트는 공식·사용 빈도 기반 지원 지표가 아닙니다. |

리포트는 기능군별 연결 시나리오의 모델별 증거 상태도 표시합니다. 오프라인 결과는 실모델 기능을 입증하지 못하고, 연결 시나리오가 모두 통과해도 부분 범위가 완전한 지원으로 승격되지는 않습니다.

## 검사하는 네이티브 경로

- **C11:** 실제 `bin/codex-ghcp`·생산 bridge 수명·기본 도구 카탈로그. `model_catalog_json`·patch 프로파일을 주입하지 않습니다. 대화형 모델 선택이나 모든 reasoning 설정을 인증하지는 않습니다.
- **C12:** 네이티브 `review/start`와 reviewer 시작·종료 이벤트. 리뷰처럼 보이는 일반 프롬프트로 대체하지 않습니다. bridge가 지원하지 않는 구조화 출력이 필요하면 **unsupported**로 남깁니다.
- **C13:** 네이티브 Plan 모드와 사용자 질문/응답 상관관계. 모델에게 미리 알려주지 않은 호스트 응답이 파일 변경 없이 계획에 반영되어야 합니다.
- **C14:** 12 KiB 이상 문맥·명시적 로컬 압축·새 프로세스 재개. 최대 토큰·자동/원격 압축·장기 부하 검증은 아닙니다.
- **C15:** 실제 실행 중인 소유 명령을 관측한 뒤 중단하고, 백그라운드 터미널을 명시적으로 정리하여 프로세스 종료와 같은 thread의 후속 실행을 확인합니다.
- **C16:** 소유 HTTP MCP·임시 Bearer 인증·비인증 거절·발견/리소스/오류 복구. 외부 OAuth·플러그인 설치 검증은 아닙니다.
- **C17:** 읽기 전용 자식 에이전트의 실제 spawn/wait/close 이벤트와 별도 thread·SDK 세션을 확인합니다.
- **C18:** 추론 시작 전 표시된 503 한 건, 제한된 네이티브 HTTP 재시도, SDK 프롬프트/도구 중복 실행 방지를 확인합니다. 실패 케이스 재실행이나 SSE 중간 재시도와 다릅니다.

C03은 필드 자료형을 명시하고 JSON 의미와 표현 형식(bare JSON/단일 JSON fence)을 분리했습니다. `git -c ... diff`도 인정합니다. C05는 파이프 없는 테스트를 요구하여 종료 코드 가림을 방지합니다. 도구 목표 횟수 초과는 **효율 진단**이며, 별도의 높은 안전 상한으로 폭주를 제한합니다.

## 실행 전에 고정한 증거 해석

- C12는 완료된 네이티브 리뷰의 렌더링된 finding 또는 JSON을 읽습니다. `review.mjs:3`의 실제 결함 한 건, 실제 diff 읽기, 같은 리뷰 턴의 시작·종료와 파일 보존 조건은 그대로입니다.
- C13은 부수적인 assistant 메시지가 아니라 완료된 네이티브 `plan` 항목을 판정합니다. 숨은 호스트 응답의 상관관계와 최종 계획 반영이 필요합니다. 읽기 전용 탐색만 허용하며 파일 편집·변경 명령·광범위 승인은 허용하지 않습니다.
- Git diff 증거는 묶인 셸 명령과 Git 전역 옵션을 인식하지만, 인용된 `git diff` 문자열을 실행으로 간주하지 않습니다. 다른 경로·턴, 추가 finding, 누락된 diff, 연결되지 않거나 안전하지 않은 계획은 음성 테스트에서 거절합니다.
- C12/C13과 Git 규칙은 v4에서 고정해 v6에도 그대로 적용하며 실행 후 추가한 예외가 아닙니다. C05 명령과 C15 host PID 증거는 [v6 실행기 변경](#v6-실행기-변경)에서 구분합니다. 실검증 전에 카탈로그·구현 해시를 고정하고 실패를 보존하며, 점수를 올리기 위한 개별 재실행은 하지 않습니다.

## 격리·증거

모든 fixture는 전용 임시 HOME과 변경 허용 목록을 사용하고 사용자 dirty 파일·Git index/HEAD를 보존합니다. 네이티브 셸에는 upstream 인증을 전달하지 않습니다. 알 수 없는 callback은 거절합니다. 원본 해시가 일치하는 정확한 승인 helper와 소유 MCP 동작만 제한적으로 허용합니다. 사용자 응답은 C13의 정해진 질문에만 제공합니다. 포괄 승인이나 외부 OAuth 권한 부여는 없습니다.

C11의 실검증 관찰 계층은 실제 SDK·HTTP 경계를 기록할 뿐 생산 인자·메타데이터를 바꾸지 않습니다. SDK 교체는 오프라인 모드만 허용하고 증거 판독 시 모드를 검사합니다. 임시 MCP 인증 토큰은 헤더/증거에 보존하지 않습니다. 소유 프로세스·서버·SDK 세션 정리가 필수입니다.

native JSONL·HTTP/SSE·SDK·파일 상태·판정·정리·시나리오별 증거를 보존합니다. 검증기는 계약/구현 해시·행렬·파일 소유/해시·재계산한 판정과 효율 지표를 확인합니다. 해시는 제3자 인증이 아닙니다. 공개 전 개인정보를 검토하고 원본은 ignore된 `.runtime`에 둘 수 있습니다.

## v6 실행기 변경

v6는 OS 샌드박스를 완화하지 않고 Linux 검증의 세 가지 가정을 바로잡습니다. C05는 `node --test --experimental-test-isolation=none`으로 고정 테스트 3개를 같은 Node 프로세스에서 실행합니다. 고정 버전 샌드박스의 자식 프로세스 캡처 stdout 누락([상위 이슈](https://github.com/openai/codex/issues/18473))을 피하면서 실제 실패·성공 종료 코드, 동일 테스트 3개, 별도 입력 검사는 유지합니다. C08은 동일 측정값을 Node 스트림 대신 stdout 파일 디스크립터에 기록합니다. C15는 receipt의 namespace PID를 같은 작업 디렉터리에 있는 native host의 고유한 자식 host PID와 연결한 뒤 종료를 확인하며, 샌드박스 PID를 전역 PID로 가정하지 않습니다. 과거 실패 기록은 바꾸지 않습니다.
