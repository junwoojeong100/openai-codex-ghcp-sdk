# bridge 안정성·복구 검사

[English](STABILITY_TESTING.md) · [검증 안내](../README_KO.md#개발과-검증) · [구조](ARCHITECTURE_KO.md) · [검증 기록](validation/README_KO.md)

실제 Codex 세션에 장애를 주입하고 bridge가 안전하게 실패·복구하는지 검사합니다. **11개 시나리오 × 6개 모델 = 66건**이며, 실모델 실행은 **66/66**일 때만 통과입니다. 워크플로·TUI·내구성 검사와는 별개입니다.

실행기를 쓰는 데 이 검사는 필요하지 않습니다. 운영 제한 시간 설정과 오류 코드는 [사용 안내](USAGE_KO.md#제한-시간과-복구)에 있습니다. 남아 있는 상위 필터 실패를 포함한 기록 결과는 [검증 기록](validation/README_KO.md#기록된-결과)에 있습니다.

## 검사 실행

모든 명령은 `npm ci` 후 저장소 루트에서 실행합니다. 각 모드는 단독으로 실행할 수 있으니 목적에 맞는 것을 고르세요.

| 목적 | 모드 | 실모델 호출 |
| --- | --- | --- |
| 행렬이 검사하는 내용 확인 | [계획](#계획) | 없음 |
| 로컬 상태 처리 반복 검사 | [스트레스 검사](#스트레스-검사) | 없음 |
| 실제 Codex로 러너 확인 | [오프라인 runtime](#오프라인-runtime) | 없음 |
| 66건 전체 측정 | [실모델 행렬](#실모델-행렬) | **있음** |
| 끝난 실행 다시 확인 | [보고서 검증](#보고서-검증) | 없음 |

### 계획

Codex 설치나 Copilot 로그인이 필요하지 않습니다.

```bash
npm run test:stability -- --plan
```

### 스트레스 검사

Codex 설치나 Copilot 로그인이 필요하지 않습니다.

```bash
npm run test:stability:stress
```

SDK 대역(Copilot SDK 대신 동작하는 로컬 구현)으로 도구 왕복 100회, 정확한 재시도 100회, 대기 요청 취소 10회, SDK 복구 10회와 상태 상한을 검사한 뒤 listener·queue가 정리됐는지 확인합니다. 반복되는 상태 변화를 검사하며, 실모델이나 장시간 내구성을 검사하지는 않습니다.

### 실행 준비 사항

오프라인 runtime과 실모델 행렬에는 Node 22.12 이상, Codex **0.154.0**([설치 단계](../README_KO.md#2-의존성-설치)), 동작하는 OS 샌드박스가 필요합니다. 브라우저는 필요하지 않으며 Copilot 로그인은 실모델 행렬에만 필요합니다.

### 오프라인 runtime

실제 Codex를 SDK 대역에 연결해 실행하며 모델을 호출하지 않습니다.

```bash
npm run test:stability:runtime
```

통과하면 **오프라인 하네스 통과(11/11)**로 표시합니다. 러너를 확인한 결과이며 실모델 호환성 통과가 아닙니다.

### 실모델 행렬

**Copilot 사용량이 발생합니다.**

1. [실행 준비 사항](#실행-준비-사항)을 설치하고 [Copilot 계정 확인](../README_KO.md#3-설치와-계정-접근-확인)을 마칩니다.
2. `./bin/ghcp-models`를 실행해 기본 모델만이 아니라 **[지원 모델 6개](../README_KO.md#모델) 모두** 사용할 수 있는지 확인합니다.
3. 새 출력 디렉터리를 지정해 행렬을 실행합니다.

```bash
npm run test:stability -- --execute --output .runtime/stability-new-run
```

러너는 시작 전에 자신의 소스 사본을 출력 디렉터리에 저장합니다. 최악의 경우 약 **50.5분**이 걸립니다([시간 상한](#시간과-상한)).

### 보고서 검증

검증은 저장된 증거로 모든 판정을 다시 계산합니다. 모델을 호출하거나 케이스를 다시 실행하지 않습니다. 실패가 있어도 끝난 실행은 모두 검증하세요.

```bash
npm run test:stability -- --verify .runtime/stability-new-run/report.json
```

검증은 별도 명령으로 실행하세요. 실패가 있는 실행은 종료 코드 1로 끝나므로 `--execute` 뒤에 `&&`로 `--verify`를 연결하면 검증이 건너뛰어집니다.

**실행 후 소스가 바뀌었다면** 그 실행이 저장한 소스로 검증하세요. 출력 디렉터리 전체를 보존하고 같은 의존성을 설치해야 합니다.

```bash
node .runtime/stability-new-run/source-snapshot/scripts/stability.mjs \
  --verify .runtime/stability-new-run/report.json
```

`docs/validation`에 공개한 요약은 완전한 보고서가 아니므로 이 방법으로 검증할 수 없습니다.

## 결과 읽기

출력 디렉터리의 `report.md`(예: `.runtime/stability-new-run/report.md`)를 여세요. 읽는 순서대로 구성되어 있습니다.

1. **Result:** 판정과 통과 수
2. **Per-model results:** 모델별 통과 수
3. **Cases needing attention:** 실패한 판정, 실패 분류, 기록된 오류와 케이스 증거 링크
4. **Complete matrix:** 모든 케이스

`report.md`는 읽기용 보기일 뿐이며 `--verify`는 `report.json`을 검사합니다.

| 종료 코드 | 의미 |
| --- | --- |
| 0 | 유효한 계획, 오프라인 하네스 통과, 또는 실모델 66건과 실행 전체 조건 통과 |
| 1 | 통과하지 못했거나 미완료인 실행. 통과하지 못한 실행의 증거가 유효해도 `--verify`는 1을 반환합니다. |
| 2 | 인자 또는 증거 오류 |

**통과는 66/66뿐입니다.** 보고서에 95% 참고 기준(63/66)도 표시하지만 판정이나 종료 코드는 바뀌지 않습니다. 예를 들어 실모델 **65/66**에 `evidenceIntegrity: true`라면 통과하지 못한 실행의 유효한 증거입니다. [보고서 필드 해석](validation/README_KO.md#결과-읽기)을 참고하세요.

실패한 케이스에는 `cleanup`(우선 적용), `upstream-content-filter`, `literal-output`, 원인 미확정 중 하나의 분류를 붙입니다. 필터 분류에는 실제 native Responses 오류 코드가 필요하며, 거절처럼 보이는 문구·제어 요청·SDK 힌트만으로는 부족합니다. 분류는 실패를 설명할 뿐 판정·상태·분모·종료 코드를 바꾸지 않으며, `--verify`가 다시 계산합니다.

원시 로그는 Git에서 제외한 `.runtime` 디렉터리에 남습니다. 공유하기 전에 검토하고 민감정보를 가리세요.

## 시나리오

기본 검사 사양(버전별 시나리오·통과 기준)은 `codex-ghcp-stability-11-v5`입니다. 한 케이스는 한 모델에서 시나리오 하나를 실행한 결과이며 Codex **0.154.0**과 Copilot SDK **1.0.14**를 사용합니다.

| ID | 시나리오 | 주입 장애 | 케이스 제한 |
|---|---|---|---:|
| S01 | 네이티브 읽기·유니코드 SSE·준비 상태 | 없음 | 90초 |
| S02 | pending 결과 반환 중 도구 순서 변경 | 도구 목록 순서만 변경 | 90초 |
| S03 | 결과가 누락된 정책 변경 거절 후 완전한 원래 요청 수락 | 도구 결과를 모두 누락한 제어 요청 1회 | 90초 |
| S04 | 결과 요청 재시도·중복 제출 방지 | 동일 HTTP 요청 1회 복제 | 90초 |
| S05 | 네이티브 작업 중 대기 요청 취소 | 제한된 SDK ACK 대기·연결 취소 | 120초 |
| S06 | 전체 요청 시간 제한 후 새 네이티브 턴 복구 | 45초 요청 제한·제한된 ACK 대기 | 180초 |
| S07 | 유휴 SDK 연결 상실·새 thread 복구 | 시험 소유 SDK만 강제 종료 | 150초 |
| S08 | 도구 결과 pending 중 SDK 상실·비재실행 | 소유 네이티브 callback 시점 SDK 종료 | 150초 |
| S09 | 상태 확정 전 스트림 불일치 거절 | SDK delta 메시지 ID 1개 손상 | 120초 |
| S10 | 새 프로세스 resume·도구 중복 방지 | 소유 host·bridge의 계획된 재시작 | 150초 |
| S11 | 도구 6회 왕복·장문 문맥·로컬 압축 | 12 KiB 이상 padding·명시적 네이티브 압축 | 240초 |

표시된 시험용 프록시가 각 장애를 주입합니다. 실모델 모드에서 모델 출력을 만들어내거나 SDK를 대체하지 않습니다. 프록시의 제어 요청(복제·거절·취소하는 HTTP 요청)은 별도 케이스로 세지 않습니다.

## 통과 기준

- **66건 전체의 모든 판정이 통과해야 합니다.** 실패·미지원·차단·시간 초과·미실행 케이스도 분모에 남습니다.
- **실모델 케이스는 실제 경로를 사용합니다.** 네이티브 Codex app-server → 운영 bridge → 실제 SDK → 정확한 모델 경로와 네이티브 fixture 도구 호출, 독립 판정, 시험 소유 자원의 정리가 모두 필요합니다.
- **답에 literal 토큰이 그대로 있어야 합니다.** 읽기·회상 답은 완전한 `value:`와 `receipt:` 토큰을 포함해야 합니다. 추가 설명이나 코드 fence는 표현 진단으로 기록하며 실패가 아닙니다. 접두어·값 누락, 예상하지 않은 도구, 대응되지 않는 증거, 복구 실패는 실패입니다. 이 규칙은 워크플로 검사의 정확한 출력 판정과 다르며 그 점수를 바꾸는 데 사용할 수 없습니다.
- **예상한 장애는 실제로 실패해야 합니다.** 지정한 오류로 실패해야 하며, 성공처럼 보이는 답으로는 장애 턴을 통과할 수 없습니다.
- **다시 기회를 주지 않습니다.** 자동 케이스 재실행·모델 대체·부분 선택·OpenAI 기준선은 없습니다. 실패한 케이스를 다시 실행하거나 교체하지 않으며, 각 점수는 한 구현과 한 검사 사양의 완전한 실행 하나에 속합니다.
- **통과의 범위:** 66/66은 여러 시간 soak, 제품 지원 비율, 과거 멈춤 문제가 모두 해결됐다는 증명이 아닙니다.

## 선택적 문구 프로필

기본 프로필은 `v5`입니다. 선택적 프로필 두 개는 모델이 보는 문구만 바꿉니다.

| 프로필 | 선택 방법 | 모델이 받는 작업 |
| --- | --- | --- |
| `v5` | 기본값 | 기본 합성 표식 복사 작업 |
| `application-data-v3` | `--profile application-data-v3` | v5 기반 애플리케이션 데이터 읽기·기억·회상 문구 |
| `application-data-v4` | `--profile application-data-v4` | `value:`/`receipt:` 레이블·콜론·공백을 포함한 파일 전체 보존 명시 |

모델 호출 없이 프로필을 확인합니다.

```sh
npm run test:stability -- --plan --profile application-data-v4
```

프로필로 실행하려면 새 `--runtime` 또는 `--execute` 실행에 같은 `--profile` 옵션을 추가하세요.

- 모든 프로필은 6개 모델·11개 시나리오·fixture·장애·예산·원문 출력 및 정리 판정을 유지하며 고유한 catalog ID와 hash를 사용합니다.
- 운영 요청이나 보호 정책은 바꾸지 않습니다.
- 한 프로필의 결과로 다른 프로필을 대신할 수 없습니다. `--verify`는 기록된 프로필을 사용하고 `--profile` 재정의를 거절합니다.

## 도구 결과 전달 회귀 검사

`pending-result-instruction-handoff-v2`는 66건에 포함되지 않는 별도 검사입니다. 실제 Codex TUI·실행기·fixture MCP 서버·headless Playwright를 사용하며, 표시된 지시문 갱신을 완전한 도구 결과 배치와 함께 보냅니다.

fixture 실행 1회, 기존 결과 RPC 제출 0회, 샘플을 독립된 한 줄로 정확히 출력, `/new` 없이 다음 턴 성공이 모두 필요합니다. [이전 검사 실패](validation/2026-09-23-pending-handoff.json)는 기록에 남아 있습니다. 두 모드 모두 [TUI 준비 사항](TUI_SCENARIOS_KO.md#실행-준비-사항)이 필요합니다.

**오프라인(모델 호출 없음):** 이 명령에서 실모델 모드 변수를 제거합니다.

```sh
env -u GHCP_LIVE_HANDOFF_OUTPUT node --test test/runtime/pending-handoff.test.mjs
```

**실모델(6개 모델의 Copilot 사용량 발생):** 변수에 새 출력 디렉터리를 지정합니다.

```sh
GHCP_LIVE_HANDOFF_OUTPUT=.runtime/pending-handoff-live-new \
  node --test --test-concurrency=1 test/runtime/pending-handoff.test.mjs
```

`GHCP_LIVE_HANDOFF_OUTPUT`을 셸에 export하지 마세요. `npm run test:runtime` 안에서 실행될 때도 이 검사를 실모델 모드로 바꿉니다.

예상 오류: 결과 전달 중 정리나 준비 상태를 확인하지 못하면 bridge는 `session_handoff_failed`(503)를 반환합니다. 취소·연결 유실·대체 세션 실패 후에는 해당 대화를 새 대화로 다시 시작하지 않고 사용할 수 없는 상태로 둡니다. 결과가 누락되거나 맞지 않으면 `tool_result_mismatch`(409), 이력이 바뀌었으면 `pending_session_changed`(409)를 반환합니다.

## 참고 자료

### 시간과 상한

최대 4개 모델 lane을 병렬로 실행하며, 각 lane은 한 모델의 케이스를 순서대로 실행합니다. 전체 강제 종료 시간은 없습니다. 최악의 경우 사전 점검 90초 + 1,470초 wave 2회 = **50.5분**이며 OS·I/O 부하는 제외합니다.

| 항목 | 값 |
| --- | --- |
| 케이스별 정리 예비 시간 | 30초 |
| 작업별 정리 제한 | 5,000ms(운영 기본값) |
| ACK 준비 대기 | 45초 |
| SDK client 시작·모델 목록 초기화 | 30초 |
| S06 장애 | 전체 요청 제한 45초, ACK 대기 60초. 요청 제한이 먼저 만료됩니다. |
| 소유 프로세스 그룹 종료 대기 | 남은 케이스 시간 안에서 최대 2초 |

세션 생성에는 턴·요청 제한도 적용되며, 각 케이스는 ACK 대기 지점에 도달했음을 증명해야 합니다. 정리 오류는 케이스 실패이며, 진단은 오류 문구를 기록하지 않고 실패 단계(abort·disconnect·delete)와 시간 초과 또는 RPC 실패 여부를 표시합니다. 대기 후에도 살아 있는 프로세스 그룹은 케이스 실패입니다.

### 준비 파일과 프롬프트 규칙

- `read_fixture`는 레이블·구분자를 포함한 **UTF-8 파일 전체를 변경 없이** 반환합니다. 모든 모델·프로필이 같은 도구 설명을 받습니다.
- 도구 설명 변경은 구현 hash와 저장된 소스에 기록됩니다. catalog hash만으로는 모델 입력이 같다고 증명할 수 없습니다([과거 수정 기록](validation/2026-09-22-runner-repair/README_KO.md)).
- 한 프로필 안에서는 6개 모델이 같은 합성 표식 작업을 받습니다. 읽기·기억·회상 프롬프트는 두 줄을 그대로 출력하도록 요청하며, 기억 턴은 두 줄을 바로 출력하고 같은 턴에서 파일을 한 번 더 읽어야 합니다. 이 문구는 기존 판정에 맞춘 것이며 판정을 완화하지 않았습니다. 기본 프로필은 두 도구 결과 줄을 text fence로 출력하도록 요청합니다.
- 클라이언트 지시문은 SDK의 시스템 지시문 뒤에 그대로 추가합니다. SDK 내장 도구는 제외하고 SDK 권한 요청은 거절합니다. bridge는 도구 설명을 바꾸거나 모델 출력을 고치지 않으며, 공급자가 필터링한 턴은 실패로 남습니다.

### 검사하는 동작

시나리오는 다른 문서에 설명한 운영 동작을 검사합니다. [제한 시간과 자동 복구](USAGE_KO.md#제한-시간과-복구), [상위 필터 오류](COMPATIBILITY_KO.md#상위-서비스에서-필터링한-응답), [복구 설계](ARCHITECTURE_KO.md#안정성복구-경계)를 참고하세요. 이 검사는 사용자가 사용 중인 bridge를 재시작하지 않습니다.

### 저장되는 증거

모든 실행은 사전 점검 전에 소스 파일, 구현·catalog hash, 검사 사양을 동결합니다. 네이티브 이벤트, SDK 메시지·사용량, HTTP/SSE, 표시된 제어 요청, 독립 판정, 케이스별 감독 프로세스 기록과 전체 행렬을 보존합니다. 검증기는 저장된 통과 표시를 믿지 않고 판정·측정값·증거 요약을 다시 계산합니다. hash는 파일을 식별할 뿐 제3자 인증이 아닙니다.

CI는 한 검사의 실패가 이후 결과를 가리지 않도록 오프라인 검사를 나눠 실행하고, 민감정보를 제거한 실패 진단을 artifact로 보존합니다.

[Opus 진단](OPUS_DIAGNOSTICS_KO.md)은 fixture 프롬프트나 채점 행렬을 바꾸지 않고 네이티브 거절 메타데이터를 수집합니다. 그 결과는 행렬 결과와 섞지 마세요.

### 검사 사양 변경 이력

- `v5`는 S03을 바꿨습니다. 도구 결과가 누락된 정책 변경 요청은 거절하고, 결과가 모두 맞는 결과 전달은 수락합니다.
- 과거 `v4`·`application-data-v2`와 7개 모델 77건 사양은 더 이상 선택할 수 없습니다. 해당 기록은 저장된 소스로 검증하며 v5 기준으로 재채점하지 않습니다. 과거 결과는 [검증 기록](validation/README_KO.md)에 있습니다.
